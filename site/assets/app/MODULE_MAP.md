# app.js split module map

This file records the first split of `site/assets/app.js`. It is meant to keep later refactors honest: module state moves with its functions, high-level callbacks use action injection, and the entry module wires everything before calling `init()`.

## Wiring notes

- `app.js` imports modules statically, calls all `set*Actions(...)`, then calls `init()`.
- `router.js` does not import `history.js`; `syncUrlState()` calls injected `onUrlSync`.
- `router.js`, `history.js`, and `codex-ui.js` call masonry relayout through injected `updateVirtualCards`; they must not statically import `masonry.js` for that edge.
- `masonry.js` does not import lightbox or UI orchestration; card behavior is injected with `setMasonryActions(...)`.
- `masonry.js` calls feedback through injected `reportEntry`; `report.js` owns submission, context packing, fallback copy, and must not import masonry.
- `modal.js` owns shared mask/focus behavior; UI modules may import it directly instead of creating per-dialog focus traps.
- `access.js` owns every access gate, codex-level and entry-level: `isCodexLocked`/`firstUnlockedCodex` gate whole books, while the entry-level rating gate (`entryRating` reads a single entry's `rating` field, `isNsfwRating`/`isEntryNsfw` fold in NSFW path segments, `isEntryAccessBlocked`/`isR18gBlocked` add the R18G name/path checks) hides or locks individual entries and tree nodes. Consumed by `codex-ui.js`, `router.js`, `lightbox.js`, `history.js`, `ui.js`, `fav-codex.js`, `site-search.js`.
- `browser-history.js` owns the managed history stack (route records + overlay layers) and is page-agnostic: atlas adapts it in `router.js`, community in `../community/router.js`. Overlay handlers registered with `registerHistoryLayer` must be direct open/close functions that never touch history; the user-facing open/close wrappers decide push/replace/back. Route records carry `parentId`/`transition`/`scrollY`; **every** managed `popstate`, including pure-layer/reload-collapse early returns, invalidates the previous restore token and unlocks history writes. A layer the user opens during an async restore is preserved visually and registered only after that restore finishes if it is still open. `initializeBrowserHistory` re-adopts a managed record persisted in `history.state` so reload/cross-document return keep identity and scroll. If reload intentionally drops transient UI (layers or a community detail), initialization folds that child chain back to the nearest visible parent before user input, carrying the restored route/scroll without replaying it.
- `data.js` stores the **in-flight Promise** in `state.codexCache` before downloading/normalizing a codex. Concurrent callers share it; rejection and external-source fallback remove that exact promise so a later call can retry.
- `favorites.js` owns favorite keys and persistence; it only asks the UI layer to re-filter via injected `applyFilter`. Keys always belong to an entry's REAL codex: entries from the favorites view carry `_srcCodexId` and are resolved through `findCodexMeta`. Alias lookup is memoized by the `state.codexes` array reference, so edit-mode index reloads invalidate it naturally.
- `favorites-backup-core.js` is browser-agnostic: it owns the public V1 JSON contract, validation, alias canonicalization, deterministic serialization, restore planning, and rollback-safe writes to both favorite storage keys. `favorites-backup.js` owns the shared dialog/file flow and emits only scope metadata; `app.js` and `community.js` re-read their own in-memory favorite state after same-page or cross-tab changes.
- `fav-codex.js` builds the temporary "全部收藏" view data (id `favorites`, not registered in `state.codexes`): it merges favorited entries from all codices via `fetchCodex` (cached), resolves cross-codex image paths (codex-mode sources get `assetCodexId`, relative-mode sources get pre-resolved absolute URLs), prefixes `path` with the source codex name (tree groups by source), and tags entries with `_srcCodexId`/`_srcCodexTitle`/`_srcType`/`_srcPath`. `app.js` enters this view through `openFavoritesView()` while keeping `state.browseCodex` as the real selected codex; URL sync writes the real `codex` plus `fav=1`, and the topbar favorite toggle is the user-facing entry/exit. Consumers of `_src*`: `favorites.js` (keys), `history.js` (recent entries), `report.js` (feedback context), `masonry.js` (pack behavior).
- `site-search.js` builds the temporary "全站搜索" view data (id `site-search`, not registered in `state.codexes`): it merges entries from all currently unlocked codices via `fetchCodex` (cached), resolves cross-codex image paths with the same rules as `fav-codex.js`, prefixes `path` with the source codex name, and tags entries with `_src*` source metadata. Only a fully successful, non-fallback build is memoized; failed/degraded builds retry next time, while edit mode explicitly invalidates both this memo and the per-entry search/access caches after in-place changes. `app.js` enters this view through `openSiteSearchView()` only when `state.searchScope === "site"` and `state.query` is non-empty, and rechecks that intent after the async build and immediately before the View Transition callback. Clearing search or switching scope back to `codex` exits to `state.browseCodex`. URL sync writes the real `codex` plus `q` and `scope=site`; old `q` links without `scope` remain current-codex search.
- `copy.js` currently records copy side effects through `history.js`; `history.js` must not import `copy.js` unless that side effect is first moved to the orchestration layer.
- `ui.js` keeps `applyDensity()` as orchestration: state/localStorage/body class, control state, masonry anchor and relayout, and toast.
- `edit.js` / `edit-core.js` are the local editor (P0, see decisions/本地法典编辑器.md). They are **dynamic-import only**: `app.js maybeLoadEditMode()` probes the same-origin `/__edit__/ping` after first render (including the empty-index state; guarded by `isLocalOrigin()` + `requestIdleCallback` with a timeout because the masonry page is rarely idle) and imports `edit.js` only when the local `tools/edit_server.py` answers. Production and plain preview return 404, so the editor never loads and adds zero weight. Main-code touch-points are kept tiny and inert when the editor is absent: the probe block in `app.js`, the `lightbox:rendered` and `codex:loaded` CustomEvents, the opt-in `openLightbox(..., {allowEmpty:true})` placeholder used only to edit no-image entries, the `codexUiActions.decorateDoor?.()` hook on the picker's community door, the `emptyCategories` awareness in `buildAccessTree()` (only fires for books that have the field, i.e. ones the editor touched), and the exported `closeCodexPicker()`. `edit.js` reaches the rest through injected `{loadCodex, applyFilter, captureRoute}` and by importing `lightbox.js`/`codex-ui.js`/`modal.js` directly (same shared instances). Its dynamic dialogs use the shared modal history/focus infrastructure. It never edits virtual-view entries (`_srcCodexId`) or external-source books.
